# HANDOFF 三項待決事項 — 好壞分析

> 對應 `docs/procurement/HANDOFF.md` 三項待決事項，user 已回覆「要分析好壞再決定」
> （決定2、3）與「要接但需對應現有資料」（決定1）。本檔提供分析，最終拍板仍由 user 決定。

## 決定1：真實供應商資料要不要接進來、怎麼接

User 已拍板「要接」，但要求先跟 `gift-suppliers/` 現有資料做欄位對應確認。以下是**整合方式**
的三個選項比較（欄位對照本身已在 `docs/procurement/02_data_model.md` 最後一節完成）。

| 選項 | 優點 | 缺點 | 機密風險 |
|---|---|---|---|
| **A. 私有登入頁面**（獨立 web app + auth） | UI 友善、可多人協作、可擴充成完整 CRM | 開發/維運成本最高，需另找主機（不能放 GitHub Pages，那是公開站）、要處理登入驗證與 session 安全、資安責任加重（多一個對外服務就多一個攻擊面） | 需要新建才有存放空間，目前無現成低風險位置 |
| **B. 留在 Excel + 純加提醒腳本**（不做整合介面） | 零開發成本、user 已熟悉操作、不引入新攻擊面、資料完全不移動 | 難做「狀態變更自動觸發通知」（Excel 本身不會主動偵測變化，需額外監控檔案），多人協作困難，與現有 Apps Script 架構脫節 | 最低（維持現狀） |
| **C. Google Sheet 當資料庫**（比照現有詢價表單 Apps Script 模式） | 複用現有 LINE Channel Access Token（不用重新申請）、Google Sheet 存取控制簡單（只分享給指定帳號即可，不對外公開）、Apps Script time-driven trigger 可直接做逾期偵測與排程，不需要 user 電腦一直開機 | 需要把 Excel 主檔資料手動/半自動搬到 Sheet（一次性工），Google 帳號分享設定若手滑會外流，仍稱不上正式「有權限分級的私有 CRM」 | 中（取決於 Sheet 分享設定是否收斂到位） |

**建議**：**C**。理由是與現有詢價表單基礎設施（Apps Script + LINE 推播）同構，開發量最小，
且機密風險可控（Sheet 分享範圍限縮到 user 自己即可，等同私有）。A 選項的登入頁面開發成本
與資安責任不成比例，除非未來有多人協作需求才考慮升級。B 選項雖然最安全但無法達成「自動
逾期提醒」這個系統設計的核心目的。

**不論選哪個，動手前都要先做的事**：把 `gift-suppliers/` 主檔實際欄位內容讀出來跟
`02_data_model.md` 的欄位對照表逐一核對命名與型別是否吻合（目前欄位對照只到「欄位名稱層級」，
沒有實際讀過內容）。這一步屬於「讀取可以做，輸出只能留在 gift-suppliers/ 底下」的範圍。

## 決定2：要不要正式部署成 Apps Script

| 選項 | 優點 | 缺點 |
|---|---|---|
| **A. 留在本地 Python 雛形** | 已完成、不需要額外帳號設定、開發快、邏輯單純 | 只能在 user 電腦手動跑（`run_demo.py`/日後的正式版都一樣），無法自動排程除非另外設定 Windows Task Scheduler，且 Task Scheduler 本身又要處理「電腦沒開機就不會跑」的問題；沒有內建 LINE 推播能力，`notify_stub()` 要接 LINE Messaging API 得另外申請/管理一組 Token，跟現有詢價表單是兩套獨立系統 |
| **B. 部署成 Apps Script**（比照 `config/google-apps-script/Code.gs`） | 與現有詢價表單共用同一個 LINE Channel Access Token（不用重新申請）、Google 代管執行環境與排程，不依賴 user 電腦是否開機、資料存在 Google Sheet 方便直接查看/手動修改 | 需要 user 操作部署（Apps Script 授權、可能要在 LINE Developers Console 確認 webhook 範圍沒有衝突）、Apps Script 單次執行有時間上限（約 6 分鐘，以目前資料量不會撞到）、程式碼要從 Python 重寫成 Apps Script 的 JavaScript，雛形驗證過的邏輯需要重新對照移植 |

**建議**：**B**。核心原因是決定3（排程提醒）本質上需要「不依賴 user 電腦開機」的排程環境，
Apps Script 的 time-driven trigger 剛好解決這個問題，而且能直接複用現有 LINE 推播管線，不用
再管理第二組憑證。本地 Python 雛形的價值已經在 Phase 4 demo 驗證完成（證明資料模型/狀態機
設計可行），移植到 Apps Script 是「把驗證過的設計換一個执行環境」，不是重新設計。

**代價**：需要 user 花時間操作一次部署（跟 `scripts/setup_apps_script_form.py` 詢價表單部署
是同一類操作，可以合併一起處理，減少 user 重複跑部署流程的次數）。

## 決定3：逾期提醒排程頻率

| 選項 | 優點 | 缺點 |
|---|---|---|
| **每日一次**（如每天早上 9:00） | 雜訊最低，一天一則彙總通知不會洗版，符合「逾期」本來就是以「天」為單位判定（`reply_deadline` 是 date 型別，不是 datetime） | 若當天逾期發生在檢查時間點之後，最慢要等 24 小時才收到通知（例如晚上才過期，隔天才提醒） |
| **每小時** | 幾乎即時 | 同一筆逾期案件會被重複判定成立、重複發送通知，除非額外做「只在第一次超過期限時通知一次」的去重邏輯（目前 `tracker.py` 的 `check_overdue()` 沒有這個機制），否則會洗版，浪費卻不成比例的複雜度換取沒必要的即時性 |
| **即時 webhook 觸發** | — | **不適用**：逾期是「時間流逝」造成的狀態轉換，不是外部系統主動通知的事件，沒有對應的 webhook 來源可以觸發。真正適合 webhook 的是「廠商回覆報價」這類外部動作觸發的狀態變更，跟「逾期提醒」是不同的通知類型（`02_data_model.md` 通知觸發規則表裡已經分開列） |

**建議**：**每日一次**。理由：一是逾期判定的資料粒度本來就是「天」，更高頻率不會提升準確度
只會增加重複通知的風險；二是採購跟催本來就不是分秒必爭的場景，隔天知道不影響決策時效；
三是如果決定2選 B（Apps Script），time-driven trigger 設「每日一次」是最簡單、最省維運
心力的排程設定。

## 三項決定的相依關係

決定2選 B 會讓決定3的排程實作變簡單（Apps Script trigger 天生支援每日排程，不用另外處理
「電腦沒開機」問題）；決定1選 C 又跟決定2選 B 是同一套 Google Sheet + Apps Script 基礎設施，
三者選同一條路線（1-C / 2-B / 3-每日）可以共用一次部署工作，不用分三次各自處理。
