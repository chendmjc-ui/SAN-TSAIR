# 贈禮品尋單採購流程 — 架構研究（Phase 1）

> 隸屬 `docs/GOAL_procurement_architecture.md` Phase 1 產出。

## 業務範圍定義

「贈禮品尋單採購流程」涵蓋三才實業從**發現候選供應商**到**正式下單**的內部作業鏈：

```
候選發掘 → 初步聯繫/詢價 → 報價比較 → 樣品評估 → 決策 → 正式下單 → 交期追蹤
```

對照 `gift-suppliers/` 子專案既有作法（20 家候選廠商盡調、第一梯隊 8 家話術、MVP 測試規劃），
這套流程目前是**人工維護在 Excel 主檔**（`data/禮贈品原廠聯繫與MVP型錄規劃_助理執行版.xlsx`），
本次規劃的目標是設計一套「可選擇性升級」的半自動追蹤架構——不是要取代 Excel，是要設計
「當規模變大、需要自動提醒/自動通知時」的下一步架構長什麼樣子。

**本次產出僅止於架構設計 + 可運作雛形（用虛構資料驗證），不觸碰、不搬移 `gift-suppliers/`
內任何實際資料。**

## 參考模式一：goal-continuous-agent 多階段自跑 SOP

直接沿用本 skill 本身的核心設計，重點可轉移的原則：
- **Success/Stop/Phase 三件套**：任何自動化流程都要先定義「完成長怎樣」「什麼時候要停下找人」
  「拆成幾個可獨立驗證的階段」，而不是寫一支黑箱腳本
- **狀態外顯化**：每個階段的進度要能被讀取、被驗證（量化條件），不能只靠人記憶
- **失敗回滾表**：每種已知失敗模式要有對應處理方式，不能卡住就整條流程停擺

轉譯到採購流程：**供應商狀態機**本質上就是「Phase 拆解」的採購版；**自動提醒/通知**
本質上就是「Self-Loop 每階段檢查」的常態化版本。

## 參考模式二：LINE bot + 表單 + 後端通知架構

三才網站本身剛完成的詢價表單架構（`config/google-apps-script/Code.gs`）就是這個模式在地化
的實例：

```
前端表單（HTML/JS）
  → POST 到 Google Apps Script Web App
    → 寫入 Google Sheet（資料留底）
    → 呼叫 LINE Messaging API 推播通知（即時提醒有人動作）
```

這個「表單/事件觸發 → 資料落地 → 即時通知」三段式，正是採購追蹤系統最需要的骨架：
供應商狀態每次更新（例如「已收到報價」），都可以比照這個模式，寫入資料來源 + 推播提醒
負責人該跟進了。

**技術棧選擇**：延續同一套 Google Apps Script + Sheet + LINE 模式（成本為零、user 已經
熟悉部署流程、跟現有詢價表單共用同一組 LINE 推播基礎設施），優於另外引入新工具。

## 參考模式三：網站資訊架構／頁面組織方式

hsc.tw 是 WordPress 站台，技術棧與 SAN-TSAIR 的純靜態 GitHub Pages 不同，程式碼結構不直接
可搬。但可轉移的抽象原則是「**分類驅動的資訊組織**」：hsc.tw 依業務線/產品線分類內容，
SAN-TSAIR 型錄本身也已經是「服飾・制服系列」「企業禮贈品系列」兩大分類 + 逐廠商開關
（`VENDOR_ENABLED`）的模式。

轉譯到採購追蹤系統：**供應商資料也應該用同一套分類邏輯**（依業務線分類 + 逐廠商狀態旗標），
維持跟現有型錄系統一致的心智模型，日後如果真的要做成內部頁面，可以直接複用型錄的
分類渲染邏輯，不用另外發明一套。

## 小結：本次架構要解決的核心問題

現有 Excel 主檔的痛點（推測，非實際讀取 `gift-suppliers/` 內容得出，純架構設計考量）：
1. 狀態變化沒有即時通知，容易漏追蹤
2. 沒有結構化的狀態機，容易「卡在中間」不知道下一步該做什麼
3. 純人工維護，規模變大（供應商數量增加）時難以擴充

Phase 2-4 將針對這三點設計資料模型、狀態機、與自動化追蹤雛形。
